### SC-01: 신규 사용자 온보딩

**시나리오 ID**: SC-01  
**제목**: 신규 사용자 온보딩 (회원가입 → 로그인 → 첫 할일 등록)  
**관련 UC**: UC-01, UC-02, UC-05  
**관련 페르소나**: -  
**유형**: Happy Path

#### 사전 조건

- 사용자는 애플리케이션에 미가입 상태
- 브라우저에서 로그인 페이지에 접근 가능

#### 단계별 흐름

| 단계 | 사용자 행동 | 시스템 응답 |
|------|-----------|-----------|
| 1 | 회원가입 페이지에 접근 | 회원가입 폼(이름, 이메일, 비밀번호, 비밀번호 확인) 표시 |
| 2 | 이름: "김철수", 이메일: "kim@example.com", 비밀번호: "Password123" 입력 후 회원가입 버튼 클릭 | 계정 생성 완료. 자동 로그인 또는 로그인 페이지로 이동 |
| 3 | 로그인 페이지에서 이메일, 비밀번호 입력 후 로그인 버튼 클릭 | JWT Access Token 발급. 할일 목록 화면으로 이동 |
| 4 | 할일 목록 화면에서 "+ 새로운 할일" 버튼 클릭 | 할일 등록 모달(또는 화면) 표시 |
| 5 | 제목: "프로젝트 기획서 작성", 설명: "Q2 마케팅 프로젝트 기획서", 카테고리: "업무", 종료예정일: "2026-05-15" 입력 후 등록 버튼 클릭 | 할일이 생성되고 목록 화면에 새 항목이 표시됨 |
| 6 | 할일 목록에서 방금 등록한 할일 확인 | 새 할일 항목이 목록 최상단에 표시됨 (최신 등록순 정렬) |

#### 사후 조건

- 사용자 계정이 생성됨
- JWT Access Token이 **Zustand 메모리(authStore)에 저장**됨 (httpOnly Cookie·localStorage·sessionStorage 미사용. 탭/브라우저 닫으면 자동 소멸)
- 첫 할일이 DB에 저장됨 (createdAt, isCompleted=false 기본값)
- 시스템 기본 카테고리(일반, 업무, 개인) 중 선택한 카테고리가 할일에 연결됨

### SC-02: 출퇴근길 할일 확인 및 완료 처리

**시나리오 ID**: SC-02  
**제목**: 출퇴근길 할일 확인 및 완료 처리  
**관련 UC**: UC-02, UC-07, UC-08  
**관련 페르소나**: A (김지수, 29세 스타트업 마케터)  
**유형**: Happy Path

#### 사전 조건

- 페르소나 A(김지수)가 이미 회원가입을 완료함
- 사전에 등록된 할일 목록이 존재: "캠페인 피드백 수집"(업무, dueDate: 2026-05-12), "주간 회의 자료 준비"(업무, dueDate: 2026-05-13), "운동하기"(개인, dueDate: 2026-05-14)
- iPhone 모바일 브라우저에서 접근

#### 단계별 흐름

| 단계 | 사용자 행동 | 시스템 응답 |
|------|-----------|-----------|
| 1 | 출근길 지하철에서 애플리케이션 열기 (이미 로그인 상태) | 할일 목록 화면 표시 (반응형 모바일 레이아웃) |
| 2 | 할일 목록 확인. 오늘 마감 항목("캠페인 피드백 수집") 발견 | 모든 할일이 최신 등록순으로 표시됨. 마감일이 오늘인 항목이 시각적으로 강조될 수 있음 |
| 3 | "캠페인 피드백 수집" 항목의 완료 체크박스 클릭 | isCompleted=true로 변경. completedAt에 현재 일시 기록됨. 항목이 체크 표시됨 |
| 4 | 목록을 스크롤하여 다른 항목 확인 | "주간 회의 자료 준비"(내일 마감)와 "운동하기"(모레 마감) 항목 확인 |
| 5 | 퇴근길 다시 애플리케이션 접근. 할일 목록에서 "완료" 필터 적용 | 오전에 완료한 "캠페인 피드백 수집" 항목이 완료됨 상태로 표시됨 |
| 6 | 필터를 "미완료"로 변경 | "주간 회의 자료 준비", "운동하기" 두 항목만 표시됨 |

#### 사후 조건

- "캠페인 피드백 수집" 할일의 isCompleted=true, completedAt=현재 시간으로 DB 업데이트됨
- 페르소나 A가 모바일에서도 쉽게 할일을 추적하고 완료 처리할 수 있음을 확인
- 필터 기능을 통해 완료·미완료 할일을 분리하여 조회 가능

### SC-03: 아침 루틴 — 오늘 할일 일괄 등록 및 퇴근 전 미완료 확인

**시나리오 ID**: SC-03  
**제목**: 아침 루틴 — 오늘 할일 일괄 등록 및 퇴근 전 미완료 확인  
**관련 UC**: UC-02, UC-05, UC-07, UC-08  
**관련 페르소나**: B (박성호, 42세 중견기업 팀장)  
**유형**: Happy Path

#### 사전 조건

- 페르소나 B(박성호)가 이미 회원가입을 완료함
- Windows PC 사무용 웹 브라우저(Chrome)에서 접근
- 아침 출근 시간대

#### 단계별 흐름

| 단계 | 사용자 행동 | 시스템 응답 |
|------|-----------|-----------|
| 1 | PC에서 애플리케이션 열기. 이메일과 비밀번호로 로그인 | JWT Access Token 발급. 할일 목록 화면 표시 (데스크탑 레이아웃) |
| 2 | "+ 새로운 할일" 버튼을 클릭하여 첫 번째 할일 등록 폼 열기 | 할일 등록 모달(또는 페이지) 표시 |
| 3 | 첫 번째 할일: 제목 "팀 회의 진행", 설명 "09:00 회의실 A", 카테고리 "업무", 종료예정일 "2026-05-12" 입력 후 등록 | 할일 생성. 목록 화면으로 복귀 |
| 4 | 같은 방식으로 두 번째 할일 "보고서 검토" (업무, 2026-05-12) 등록 | 할일 생성. 목록 화면으로 복귀 |
| 5 | 같은 방식으로 세 번째 할일 "예산 승인" (업무, 2026-05-13) 등록 | 할일 생성. 목록 화면으로 복귀 |
| 6 | 할일 목록 확인: 3개의 미완료 할일이 최신 등록순으로 표시됨 | 모든 할일이 isCompleted=false 상태로 표시 |
| 7 | "팀 회의 진행" 할일의 체크박스 클릭하여 완료 처리 | isCompleted=true. completedAt에 현재 일시 기록됨 |
| 8 | "보고서 검토" 할일의 체크박스 클릭하여 완료 처리 | isCompleted=true. completedAt에 현재 일시 기록됨 |
| 9 | 퇴근 시간(오후 5시)에 애플리케이션 재접근 | 할일 목록 화면 표시 |
| 10 | 필터를 "미완료"로 설정 | "예산 승인" 항목 1개만 표시됨 (내일 마감) |
| 11 | "예산 승인"이 아직 미완료 상태임을 확인하고 담당자에게 전달 예정임을 메모 | 미완료 할일 현황 파악 완료 |

#### 사후 조건

- 아침에 등록한 3개 할일이 모두 DB에 저장됨
- "팀 회의 진행", "보고서 검토"는 completedAt 기록이 있고 isCompleted=true
- "예산 승인"은 isCompleted=false 상태 유지
- 페르소나 B가 단순·빠른 등록과 완료 체크만으로 업무를 관리할 수 있음을 확인
- 필터링을 통해 미완료 항목만 선택적으로 조회 가능

### SC-04: 카테고리별 할일 관리 + 기간 필터로 지난주 완료 회고

**시나리오 ID**: SC-04  
**제목**: 카테고리별 할일 관리 + 기간 필터로 지난주 완료 회고  
**관련 UC**: UC-02, UC-07, UC-08  
**관련 페르소나**: C (이하은, 34세 대기업 기획자)  
**유형**: Happy Path

#### 사전 조건

- 페르소나 C(이하은)가 이미 회원가입을 완료함
- 다양한 기기(회사 PC, 개인 맥북, iPhone)에서 접근 가능
- 사전에 등록된 할일 목록:
  - 업무: "분기 전략 계획"(dueDate: 2026-05-12, completedAt: 2026-05-10)
  - 업무: "팀 회의 자료"(dueDate: 2026-05-13, completedAt: 2026-05-11)
  - 자기계발: "영어 강의 수강"(dueDate: 2026-05-14, completedAt: 2026-05-09)
  - 이직준비: "포트폴리오 작성"(dueDate: 2026-05-15, isCompleted: false)
  - 기타 할일들
- 오늘: 2026-05-12 (월요일)

#### 단계별 흐름

| 단계 | 사용자 행동 | 시스템 응답 |
|------|-----------|-----------|
| 1 | 회사 PC에서 애플리케이션 열기. 로그인 | 할일 목록 화면 표시 |
| 2 | 카테고리 필터를 "업무"로 설정 | 업무 카테고리에 속한 할일만 표시 ("분기 전략 계획", "팀 회의 자료") |
| 3 | 목록 확인 후, 기간 필터를 적용하려고 시도. 시작일: "2026-05-05", 종료일: "2026-05-11" (지난주) 입력 | 지난주 기준으로 dueDate가 2026-05-05~2026-05-11에 속하는 할일 조회 |
| 4 | 필터 결과: "분기 전략 계획"(dueDate: 2026-05-12, 범위 밖이므로 표시 안 됨), "팀 회의 자료"(dueDate: 2026-05-13, 범위 밖이므로 표시 안 됨) | 현재 필터(업무 + 2026-05-05~2026-05-11)에 매칭하는 할일 없음 (범위 밖) |
| 5 | 시간 범위를 조정: 시작일 "2026-05-09", 종료일 "2026-05-12"로 변경 | 지난주 금요일부터 오늘까지. "분기 전략 계획"(dueDate: 2026-05-12) 표시 |
| 6 | 카테고리 필터를 제거하고, 완료 필터를 "완료됨"으로 설정하여 지난주(2026-05-05~2026-05-11) 범위 내 완료된 모든 할일 조회 | "분기 전략 계획"(업무, completedAt: 2026-05-10), "팀 회의 자료"(업무, completedAt: 2026-05-11), "영어 강의 수강"(자기계발, completedAt: 2026-05-09) 표시 |
| 7 | 페르소나 C가 지난주 완료 항목들을 리뷰하여 자신의 성과를 확인 | 주간 회고 작업 완료. "이번 주는 3개 항목을 완료했고, 포트폴리오는 아직 진행 중" 등의 인사이트 도출 가능 |
| 8 | 개인 맥북에서 재접근 | 같은 계정으로 로그인하면 데이터가 동기화됨. 모든 할일과 필터 설정을 멀티 기기에서 일관성 있게 조회 가능 |
| 9 | iPhone에서도 재접근 (모바일 반응형 레이아웃) | 모바일 화면에 최적화된 레이아웃으로 동일한 데이터 표시 |

#### 사후 조건

- 페르소나 C가 여러 기기에서 동일한 데이터를 일관성 있게 조회 가능
- 카테고리별 필터링으로 업무/자기계발/이직준비를 체계적으로 분리 관리 가능
- 기간 필터(dueDate 기준)를 통해 특정 주간의 완료 항목을 회고할 수 있음
- 다중 필터(카테고리 + 완료 상태 + 기간)를 조합하여 상세한 조회 가능

### SC-05: 사용자 정의 카테고리 생성 후 할일 분류

**시나리오 ID**: SC-05  
**제목**: 사용자 정의 카테고리 생성 후 할일 분류  
**관련 UC**: UC-02, UC-09, UC-05, UC-07  
**관련 페르소나**: A (김지수, 29세 스타트업 마케터)  
**유형**: Happy Path (P1 포함)

#### 사전 조건

- 페르소나 A(김지수)가 이미 회원가입을 완료함
- 시스템 기본 카테고리(일반, 업무, 개인)가 자동 제공됨
- 현재 기본 카테고리만으로는 마케팅 업무의 세부 분류가 어려움을 느낌
- iPhone 모바일 브라우저에서 접근

#### 단계별 흐름

| 단계 | 사용자 행동 | 시스템 응답 |
|------|-----------|-----------|
| 1 | 애플리케이션 열기 및 로그인 | 할일 목록 화면 표시 |
| 2 | 설정 또는 카테고리 관리 메뉴에 접근 | 카테고리 목록 화면 표시: 기본 카테고리(일반, 업무, 개인) 및 "새 카테고리 추가" 버튼 |
| 3 | "+ 새 카테고리 추가" 버튼 클릭 | 카테고리 생성 모달(또는 폼) 표시 |
| 4 | 카테고리 이름 입력: "캠페인 관리" 입력 후 생성 버튼 클릭 | 새 카테고리 "캠페인 관리"가 생성됨. 사용자 정의 카테고리로 저장됨. 카테고리 목록에 추가됨 |
| 5 | 같은 방식으로 두 번째 카테고리 "회의 준비" 생성 | 새 카테고리 "회의 준비"가 생성됨 |
| 6 | 카테고리 목록: 기본 3개 + 사용자 정의 2개 = 총 5개 카테고리 확인 | 시스템 기본 카테고리는 잠금 표시(수정·삭제 불가) |
| 7 | 할일 목록으로 돌아가기. 새로운 할일 등록 | 할일 등록 모달 표시 |
| 8 | 새 할일: 제목 "Q2 페이스북 캠페인 기획", 카테고리 "캠페인 관리", 종료예정일 "2026-05-15" 입력 후 등록 | 할일이 "캠페인 관리" 카테고리로 저장됨 |
| 9 | 새 할일: 제목 "월요일 팀 회의", 카테고리 "회의 준비", 종료예정일 "2026-05-12" 입력 후 등록 | 할일이 "회의 준비" 카테고리로 저장됨 |
| 10 | 할일 목록에서 카테고리 필터를 "캠페인 관리"로 설정 | "Q2 페이스북 캠페인 기획" 항목만 표시됨 |
| 11 | 필터를 "회의 준비"로 변경 | "월요일 팀 회의" 항목만 표시됨 |

#### 사후 조건

- 사용자 정의 카테고리 "캠페인 관리", "회의 준비"가 DB에 저장됨 (isDefault=false)
- 새 카테고리들이 해당 사용자의 카테고리 목록에만 노출됨 (userId 소유권 검증)
- 새 카테고리로 할일을 등록할 수 있음
- 카테고리별 필터링으로 새 카테고리에 속한 할일을 선택적으로 조회 가능
- 시스템 기본 카테고리는 여전히 수정·삭제 불가 (BR-08, BR-10)

### SC-E01: 이메일 중복 회원가입 시도

**시나리오 ID**: SC-E01  
**제목**: 이메일 중복 회원가입 시도  
**관련 UC**: UC-01  
**관련 비즈니스 규칙**: BR-02  
**유형**: Exception

#### 사전 조건

- 이메일 "john@example.com"으로 이미 가입된 계정이 존재
- 새로운 사용자가 회원가입 페이지에 접근

#### 단계별 흐름

| 단계 | 사용자 행동 | 시스템 응답 |
|------|-----------|-----------|
| 1 | 회원가입 페이지에서 이름 "John Doe", 이메일 "john@example.com", 비밀번호 "NewPass123" 입력 후 회원가입 버튼 클릭 | 서버 검증: 이메일 "john@example.com"이 이미 존재함 |
| 2 | - | HTTP 409 Conflict 응답 |
| 3 | - | 에러 메시지 표시: "이미 가입된 이메일입니다. 다른 이메일을 사용해주세요." |
| 4 | 다른 이메일 "john.doe@example.com" 입력 후 재시도 | 입력값 검증 통과 |
| 5 | - | 계정 생성 완료 |

#### 사후 조건

- 중복된 이메일로는 새 계정이 생성되지 않음
- HTTP 409 상태 코드로 클라이언트에 명확한 에러 신호 전달
- 사용자가 다른 이메일로 재시도할 수 있도록 가이드

#### 예상 에러 응답

```json
{
  "error": {
    "code": "DUPLICATE_EMAIL",
    "message": "이미 가입된 이메일입니다."
  }
}
```

### SC-E02: 과거 날짜로 종료예정일 등록 시도

**시나리오 ID**: SC-E02  
**제목**: 과거 날짜로 종료예정일 등록 시도  
**관련 UC**: UC-05, UC-06  
**관련 비즈니스 규칙**: BR-07  
**유형**: Exception

#### 사전 조건

- 사용자가 로그인 상태
- 오늘 날짜: 2026-05-12
- 할일 등록 또는 수정 화면 접근

#### 단계별 흐름

| 단계 | 사용자 행동 | 시스템 응답 |
|------|-----------|-----------|
| 1 | 할일 등록 모달에서 제목 "지난주 보고서", 카테고리 "업무" 입력 | 폼의 일부가 채워짐 |
| 2 | 종료예정일을 "2026-05-10" (과거 날짜)로 입력 후 등록 버튼 클릭 | 클라이언트 유효성 검사(선택사항): "종료예정일은 오늘 이후 날짜여야 합니다." 알림 표시 가능 |
| 3 | 클라이언트 검사를 우회한 경우, 서버로 요청 전송 | 서버 검증: dueDate < today 조건 위반 |
| 4 | - | HTTP 422 Unprocessable Entity 응답 |
| 5 | - | 에러 메시지 표시: "종료예정일은 오늘(2026-05-12) 이후로 설정해야 합니다." |
| 6 | 종료예정일을 "2026-05-12" (오늘)로 수정 후 재시도 | 검증 통과 |
| 7 | - | 할일이 생성됨 |

#### 사후 조건

- 과거 날짜의 dueDate로는 할일이 생성되지 않음
- HTTP 422 상태 코드로 유효성 검사 오류 명확히 전달
- 사용자가 유효한 날짜로 재입력할 수 있도록 가이드
- 당일(2026-05-12) 포함 이후 날짜는 허용

#### 예상 에러 응답

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "입력값이 유효하지 않습니다.",
    "fields": [
      {
        "field": "dueDate",
        "message": "종료예정일은 오늘 이후 날짜여야 합니다."
      }
    ]
  }
}
```

### SC-E03: 타인 할일 수정 시도

**시나리오 ID**: SC-E03  
**제목**: 타인 할일 수정 시도  
**관련 UC**: UC-06  
**관련 비즈니스 규칙**: BR-03  
**유형**: Exception

#### 사전 조건

- 사용자 A(userId: uuid-1111)가 로그인 상태
- 사용자 B(userId: uuid-2222)가 생성한 할일 ID: "todo-5555"가 존재
- 악의적 또는 실수로 타 사용자 할일의 수정을 시도

#### 단계별 흐름

| 단계 | 사용자 행동 | 시스템 응답 |
|------|-----------|-----------|
| 1 | 브라우저 개발자 도구 또는 API 클라이언트를 통해 타인 할일 ID "todo-5555"의 수정 요청 시도. 요청: PUT /api/todos/todo-5555 | 서버에서 JWT 토큰에서 userId(uuid-1111) 추출 |
| 2 | - | 소유권 검증: 할일 "todo-5555"의 소유자(uuid-2222) != 현재 사용자(uuid-1111) |
| 3 | - | HTTP 403 Forbidden 응답 |
| 4 | - | 에러 메시지 표시: "이 할일을 수정할 권한이 없습니다." 또는 "요청하신 리소스에 접근할 수 없습니다." |
| 5 | 사용자가 자신의 할일 목록으로 돌아감 | 본인의 할일만 수정 가능 |

#### 사후 조건

- 타인 할일은 수정되지 않음
- HTTP 403 상태 코드로 권한 부재를 명확히 전달
- 소유권 검증(BR-03)이 모든 TODO API에서 적용됨
- 접근 시도가 로그될 수 있음 (향후 감시 대상)

#### 예상 에러 응답

```json
{
  "error": {
    "code": "FORBIDDEN",
    "message": "이 리소스에 접근할 권한이 없습니다."
  }
}
```

### SC-E04: 비밀번호 정책 위반 회원가입

**시나리오 ID**: SC-E04  
**제목**: 비밀번호 정책 위반 회원가입  
**관련 UC**: UC-01  
**관련 데이터 제약**: DC-05  
**유형**: Exception

#### 사전 조건

- 사용자가 회원가입 페이지에 접근
- 비밀번호 정책: 최소 8자, 영문(a-zA-Z) + 숫자(0-9) 각 1자 이상 필수 (DC-05)

#### 단계별 흐름

| 단계 | 사용자 행동 | 시스템 응답 |
|------|-----------|-----------|
| 1 | 회원가입 폼에서 이름 "Jane", 이메일 "jane@example.com", 비밀번호 "password" 입력 후 회원가입 버튼 클릭 | 클라이언트 유효성 검사(선택사항): "비밀번호는 최소 8자 이상이어야 합니다." 알림 표시 가능 |
| 2 | 클라이언트 검사를 우회한 경우, 서버로 요청 전송 | 서버 검증: 비밀번호 "password"는 8자 이상이지만 숫자 미포함 |
| 3 | - | HTTP 422 Unprocessable Entity 응답 |
| 4 | - | 에러 메시지 표시: "비밀번호는 영문과 숫자를 모두 포함해야 합니다." |
| 5 | 비밀번호를 "Pass123" (6자)로 변경하여 재시도 | 서버 검증: 6자 < 8자 (최소 길이 미충족) |
| 6 | - | HTTP 422 응답 |
| 7 | - | 에러 메시지 표시: "비밀번호는 최소 8자 이상이어야 합니다." |
| 8 | 비밀번호를 "Password123"로 변경 | 영문 포함, 숫자 포함, 8자 이상 조건 모두 만족 |
| 9 | - | 검증 통과. 계정 생성 완료 |

#### 사후 조건

- 비밀번호 정책을 위반하는 계정은 생성되지 않음
- HTTP 422 상태 코드로 유효성 검사 오류 전달
- 클라이언트에 정책 요구사항을 명확히 제시하여 재입력 유도
- 모든 비밀번호는 bcrypt로 해시 저장됨 (평문 저장 금지)

#### 예상 에러 응답

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "입력값이 유효하지 않습니다.",
    "fields": [
      {
        "field": "password",
        "message": "비밀번호는 최소 8자 이상이며, 영문과 숫자를 모두 포함해야 합니다."
      }
    ]
  }
}
```

### SC-E05: 카테고리명 중복 생성 시도

**시나리오 ID**: SC-E05  
**제목**: 카테고리명 중복 생성 시도  
**관련 UC**: UC-09  
**관련 비즈니스 규칙**: BR-10  
**유형**: Exception

#### 사전 조건

- 사용자가 로그인 상태
- 사용자가 이미 "마케팅" 이라는 사용자 정의 카테고리를 생성함
- 카테고리명 정책: 대소문자 무시 중복 불가, 앞뒤 공백 trim 후 검증 (BR-10)

#### 단계별 흐름

| 단계 | 사용자 행동 | 시스템 응답 |
|------|-----------|-----------|
| 1 | 카테고리 관리 화면에서 "+ 새 카테고리 추가" 버튼 클릭 | 카테고리 생성 모달 표시 |
| 2 | 카테고리 이름 "마케팅" 입력 후 생성 버튼 클릭 | 서버 검증: 사용자의 카테고리 목록에서 "마케팅" 존재 확인 (대소문자 무시) |
| 3 | - | HTTP 409 Conflict 응답 |
| 4 | - | 에러 메시지 표시: "이미 존재하는 카테고리 이름입니다." |
| 5 | 사용자가 다른 이름 "마케팅 -Q2" 입력 후 재시도 | 서버 검증: "마케팅 -Q2"는 기존 카테고리와 다름 |
| 6 | - | 카테고리 생성 완료 |
| 7 | 또 다른 시도: "  마케팅  " (앞뒤 공백 포함) 입력 | 서버 검증: 공백 trim 후 "마케팅"이 됨. 중복 확인 |
| 8 | - | HTTP 409 Conflict 응답 |
| 9 | - | 에러 메시지 표시: "이미 존재하는 카테고리 이름입니다." |
| 10 | 사용자가 "마케팅" 대신 "마케팅팀" 입력 후 재시도 | 서버 검증: "마케팅팀"은 신규 카테고리명 |
| 11 | - | 카테고리 생성 완료 |

#### 사후 조건

- 동일한 카테고리명(대소문자 무시)으로는 중복 생성 불가
- 앞뒤 공백은 자동 trim되어 저장됨
- HTTP 409 상태 코드로 중복 에러 명확히 전달
- 중복 검증은 같은 사용자 내에서만 적용 (다른 사용자는 같은 이름의 카테고리 생성 가능)
- 기본 카테고리("일반", "업무", "개인")와는 별도로 관리됨

#### 예상 에러 응답

```json
{
  "error": {
    "code": "DUPLICATE_CATEGORY",
    "message": "이미 존재하는 카테고리 이름입니다."
  }
}
```
