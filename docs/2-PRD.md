## 1. 제품 개요

### 1.1 목적

20대~50대 직장인이 업무 및 일상의 할일을 효율적으로 등록·추적·완료 처리할 수 있는 인증 기반 할일 관리 웹 애플리케이션을 제공한다. 계정 단위의 데이터 격리로 개인화된 환경을 보장하며, 카테고리와 다양한 필터를 통해 체계적인 업무 관리를 지원한다.

### 1.2 배경 및 문제 정의

직장인은 업무·개인 할일이 혼재되어 우선순위 파악이 어렵고, 기존 메모·이메일 기반 관리는 완료 추적과 기간 관리가 불편하다. 본 제품은 직관적인 UI와 필터링 기능으로 이 문제를 해결한다.

### 1.3 성공 지표 (MVP 기준)

| 지표                             | 목표    |
| -------------------------------- | ------- |
| 회원가입 → 최초 할일 등록 완료율 | ≥ 80%   |
| 핵심 API 응답 시간 (p95)         | ≤ 500ms |
| 동시 접속 300명 기준 에러율      | ≤ 1%    |

## 3. 기술 스택

### 3.1 전체 구성

```
[클라이언트]
React 19 + TypeScript
Zustand (전역 상태 관리)
TanStack Query (서버 상태·캐싱)
axios (HTTP 클라이언트)
반응형 CSS (Mobile-first)

[서버]
Node.js 22 LTS + Express 4.x (REST API)
JWT 인증 미들웨어
Joi (입력 검증)

[데이터베이스]
PostgreSQL 17
pg 라이브러리 (DB 연동 필수, ORM 미사용)

[인증]
1차: JWT (Access Token)
2차: OAuth Social (Google, Facebook 등) — 확장 예정
```

### 3.2 기술 선택 근거 및 제약

| 항목            | 내용                                                                |
| --------------- | ------------------------------------------------------------------- |
| DB 연동         | `pg` 라이브러리만 사용. ORM(Sequelize, Prisma 등) 사용 금지         |
| JWT             | Access Token 단일 방식으로 1차 구현. Refresh Token은 2차에서 검토   |
| OAuth           | 2차 확장을 고려해 인증 레이어를 전략 패턴으로 설계                  |
| 상태 관리       | 서버 데이터는 TanStack Query, 클라이언트 전용 UI 상태는 Zustand     |
| HTTP 클라이언트 | 프론트엔드에서 `axios` 사용. TanStack Query의 queryFn 내부에서 호출 |
| 입력 검증       | 백엔드 미들웨어에서 `Joi`로 요청 바디·쿼리 파라미터 검증            |
| Node.js 버전    | Node.js 22 LTS. Express 4.x                                         |

## 6. 상세 기능 명세 (MVP)

### UC-01 회원가입

- **입력**: 이메일, 비밀번호, 이름
- **성공 조건**: 계정 생성 후 자동 로그인 또는 로그인 페이지 이동
- **실패 조건**:
  - 이메일 중복 → 409 Conflict
  - 비밀번호 정책 위반(8자 미만, 영문·숫자 미포함) → 422
  - 필수값 누락 → 422

### UC-02 로그인

- **입력**: 이메일, 비밀번호
- **성공 조건**: JWT Access Token 발급 → **Zustand 메모리에 저장** (httpOnly Cookie·localStorage·sessionStorage 미사용)
- **실패 조건**:
  - 존재하지 않는 이메일 또는 비밀번호 불일치 → 401 (보안상 동일 메시지 반환)

### UC-03 로그아웃

- **동작**: 클라이언트 토큰 삭제 (1차 JWT Stateless 방식 — 서버 블랙리스트 미적용)
- **결과**: 로그인 페이지로 이동
- **설계 근거**: 소규모 개인 프로젝트 일정(3일) 내 서버 블랙리스트 구현 비용 대비 효과가 낮음. 토큰 만료 시간을 짧게 설정하여 보안 리스크 최소화. 2차에서 Refresh Token + 블랙리스트 방식으로 전환 검토.

### UC-05 할일 등록

- **입력**: 제목(필수), 설명(선택), 종료예정일(선택), 카테고리(필수)
- **제약**: 제목 최대 200자, 종료예정일은 오늘 이후(당일 포함) (BR-07, DC-03)
- **기본 카테고리**: 기본 카테고리 목록 조회 API 제공 → UI에서 선택

### UC-06 할일 수정

- **입력**: 제목, 설명, 종료예정일, 카테고리 (모두 수정 가능)
- **제약**: UC-05와 동일한 입력 제약 적용. 본인 할일만 수정 가능 (BR-03)

### UC-07 할일 목록 조회

- **기본 정렬**: 최신 등록순 (createdAt DESC)
- **필터 조합**:
  - 카테고리 (categoryId)
  - 완료 여부 (isCompleted: true / false / 전체)
  - 기간: **dueDate(종료예정일) 기준** startDate ~ endDate (DC-08)
- **필터 기준 근거**: 사용자 관점에서 "이번 주 마감 할일"처럼 종료예정일 기준 조회가 주요 사용 패턴. createdAt 기준은 관리·감사 목적으로 1차에서 불필요.
- **제약**: 기간 필터 시 startDate ≤ endDate (DC-08)

### UC-08 할일 완료 처리 / 완료 취소

- **완료 처리**: isCompleted = true, completedAt = 현재 일시 자동 기록 (BR-06)
- **완료 취소**: isCompleted = false, completedAt = null 초기화 (BR-06)
- **제약**: 본인 할일만 처리 가능 (BR-03)

### UC-12 할일 삭제

- **동작**: 본인의 특정 할일을 영구 삭제. 소프트 삭제 미적용 — 복구 불가
- **제약**: 본인 할일만 삭제 가능 (BR-03). 존재하지 않는 ID → 404

### UC-13 회원 탈퇴

- **동작**: 계정 및 연관 데이터(할일·사용자 정의 카테고리) 즉시 하드 삭제 (DC-01)
- **처리**: DB 외래키 ON DELETE CASCADE로 연쇄 삭제. 별도 트랜잭션 불필요.
- **결과**: 토큰 무효화(클라이언트 삭제) → 로그인 화면 이동

### UC-09 사용자 정의 카테고리 생성 (P1)

- **입력**: 카테고리 이름 (1~50자, 앞뒤 공백 trim 후 저장)
- **제약**: 동일 사용자 내 이름 중복 불가(대소문자 무시) → 409 (BR-10, DC-04)

## 8. 데이터베이스 설계 방향

- PostgreSQL 17 사용
- 모든 ID: UUID (gen_random_uuid())
- 타임스탬프: TIMESTAMPTZ (UTC 기준)
- 외래키 제약: ON DELETE CASCADE (User → Todo, User → Category)
- 기본 카테고리 seed: 애플리케이션 초기 실행 시 INSERT (중복 방지: ON CONFLICT DO NOTHING)
  - `일반` (isDefault=true)
  - `업무` (isDefault=true)
  - `개인` (isDefault=true)
- BR-09 적용: 사용자 정의 카테고리 삭제 시, 해당 카테고리 할일 → `일반` 카테고리로 이관 후 삭제 (트랜잭션 처리)
